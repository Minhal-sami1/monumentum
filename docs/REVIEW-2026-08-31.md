## BLOCKER

### B1 — the documented fresh-clone gate failed on stock Linux

**Upheld, and it was the real thing.** `conformance/runner.py` pinned the
interpreter with `Path.resolve()`, which follows symlinks. A Linux venv's
`bin/python` is a symlink to the system interpreter, so resolving it dropped
the virtualenv and every case failed with `No module named 'monumentum'`.
Windows venvs *copy* `python.exe`, so the defect was invisible on the only
platform I had tested.

- **Reproduced** in a clean `python:3.11-slim` container before changing
  anything: `make verify` exit 2, conformance 0/15.
- **Fixed** exactly as the reviewer proposed, using lexical normalization
  (`os.path.normpath`) so the symlink name is preserved.
- **Re-verified** on a fresh `git clone` of the committed state inside a
  clean Linux container, running the documented gate with no overrides:
  `make setup` 0, `make verify` 0, conformance 15/15, 136 tests, scenarios
  5/5, adversarial 7/7, `make reproduce` 0.
- **Guarded** by `tests/test_runner_pinning.py`. On Linux the symlink branch
  is active; I confirmed the guard fails if `resolve()` is reintroduced.
- **Audited** the remaining `resolve()` calls: those in `workspace.py`
  perform containment checks, where following symlinks is correct (a
  symlinked target escaping the workspace must be caught). The shell
  runners build paths by concatenation and were never affected.
- Recorded as DEC-041; the STATUS gate table is now split by platform.

**The wider correction:** my earlier report claimed the fresh-clone gate
green without qualification. It was green on Windows and red on Linux. A
cross-platform claim from single-platform evidence is precisely the error
this project is built to prevent, and I made it.
